## 1. Project Overview

**Temakinho** is a Japanese-Brazilian fusion sushi restaurant chain ("Japanese sushi, Brazilian soul") with locations across Italy, France, and beyond (Milano, Roma, Bologna, Lione, Rimini, Reggio Calabria, Capo d'Orlando at last count). This project is a full digital rebrand and rebuild of its website.

**The project has run in two eras:**

- **Era 1 — Strategy & Design System authorship.** An AI Product Architect role produced a strict-phase-gated chain of frozen strategy documents: Discovery → Creative Strategy → Information Architecture → Design Foundations / Component Inventory / Component Specifications / Content Strategy → Page Blueprints → Design System Specification. These live in `/Users/carlodesantis/Desktop/carlo/CLAUDE/REDESIGN/TMK/` as files `01_DISCOVERY.md` through `15_DESIGN_SYSTEM_REVIEW.md` plus `README.md`. They are **frozen** — never edit them during this phase.
- **Era 2 — WordPress/Elementor implementation (current).** The role shifted to Senior WordPress Developer / Senior Elementor Pro Developer / Front-end Engineer / Motion Developer / Technical Lead, tasked with faithfully translating an already-approved Claude Design prototype into a production-ready WordPress site. **This is the era you are in.**

**Redesign goals:** translate the approved Claude Design visual implementation into a production WordPress + Elementor Pro build with maximum fidelity — layouts, typography, spacing, imagery, color, motion, responsive behavior, navigation, and page hierarchy should be visually indistinguishable from the approved design. The Local WP install is not a prototype — it is meant to become the production implementation, migratable without redesign.

**Implementation philosophy:**
- Never redesign, never reinterpret. Translate, don't invent.
- Strict three-tier source-of-truth priority (Section 2).
- "Systems before pages" — the shared foundation (tokens, typography, header, footer, motion, shared components) must exist before any individual page, so pages consume the system instead of redefining it.
- Flag ambiguity rather than guess. Cite sources for claims. Disclose limitations (e.g. inability to visually verify without a browser) rather than overstate confidence.
- Per-page workflow: read the current Claude Design implementation for that page → compare with TMK documentation for intent → build in WordPress/Elementor → verify → only then continue to the next page.

**Current development stage:** the Foundation milestone is **complete and declared production-ready** (see Section 10 of the Production Readiness Declaration, reproduced conceptually in Section 10 of this document). The Homepage is the first page and is ~95% built — every section is live and verified except the Hero's illustration image, which is blocked on an asset problem (Section 7 / Section 10). No other page has been started. **This handoff is happening specifically so the remaining pages can be built with real visual verification in a browser, which the outgoing session could not do.**

## 2. Source of Truth Hierarchy

There are three sources of truth, in a strict, non-negotiable priority order:

1. **The current Claude Design project** (MCP tool `DesignSync`, project name "TMK Design System", `projectId: 30e72d9e-76c7-44af-9f0a-e810e3af90b9`). This is the authoritative, approved **visual implementation**. If it differs from the older TMK documentation, **Claude Design wins**.
2. **The TMK documentation** (`/Users/carlodesantis/Desktop/carlo/CLAUDE/REDESIGN/TMK/`, files 01-15 + README). Use these to understand **why** something exists — intent, architecture, rationale. **Never use them to override the approved design.**
3. **Engineering judgement.** Only when something is genuinely undefined by both of the above. Never redesign. Never reinterpret. When you exercise judgement, document the decision (see Section 8's format) so it isn't silently repeated or reversed later.

**How to resolve a conflict, step by step:**
1. Fetch the actual current Claude Design source for the component/page in question (the `.jsx` file, its `.d.ts`, its `.prompt.md`, and any relevant `guidelines/*.html` card). Do not rely on memory of an earlier fetch — re-fetch, because the Claude Design project can change between sessions.
2. If Claude Design's implementation is unambiguous, build to match it exactly. Stop here — do not consult the TMK docs to "correct" it.
3. If Claude Design is silent on the specific question (e.g. a data-binding mechanism it can't express, like looping over a WordPress taxonomy), consult the TMK docs to understand the intended architecture, then use engineering judgement to implement the mechanism — never to change what's already visually specified.
4. If both are silent, use engineering judgement, and write it down as a new entry in Section 8's decision log format.
5. If you're not sure which case you're in, ask the user rather than guess.

**A documented example of this priority order being violated and corrected:** early in this project the CV field of the Job Application Form was about to be built as a file-upload control because the TMK docs (§19 of `06_COMPONENT_SPECIFICATIONS.md`) said "file-upload," but Claude Design's actual `JobApplicationForm.jsx` implements it as a URL field. The correct call — confirmed by the user — is to match Claude Design's URL field, not the outdated doc description. **If you ever find yourself about to build something because "the docs say so" while Claude Design's actual source shows something else, stop and default to Claude Design.**

### CSS architecture — the enforced layer chain

```
tokens → base → utilities → animations → components → layout → pages
```

This is not a convention, it's mechanically enforced in `inc/enqueue.php`: `tmk_ds_enqueue_style_chain()` registers each layer's stylesheets with the **last handle of the previous layer** as their dependency. It is structurally impossible to load a component before its tokens, or a page override before its layout. Before creating any new CSS file, decide which layer it belongs to using the docblock at the top of `inc/enqueue.php` — it defines each layer's exact purpose. **`css/pages/` is currently empty and should stay nearly empty** — a page needing its own CSS file is a sign something should have been a component instead; only add a page-specific file when something is genuinely one-page-only, and promote it to `css/components/` the moment a second page needs it.

### JS architecture

```
animations (shared motion) → interactions (generic, reusable) → navigation (region-specific) → components (single-widget behaviour)
```

`js/interactions/drawer.js` and `js/interactions/accordion.js` are deliberately generic: Drawer supports any number of independent instances via matching `id`/`data-tmk-drawer-trigger`/`data-tmk-drawer-scrim` values (not hardcoded to the header's mobile nav), and Accordion scopes its "close the others" behaviour per `[data-tmk-accordion]` group wrapper so multiple independent accordions on one page never interfere with each other. **Reuse these for any future Drawer/Accordion instance (e.g. a Filters panel, an FAQ block) — do not write a new drawer/accordion script.**

### Tokens

Three-tier per the Design System Specification: **primitive → semantic → component**, all as CSS custom properties.
- Primitives: `--tatami-*` (warm cream neutral, 50-900), `--ember-*` (terracotta action accent), `--lagoa-*` (deep teal, aqua concept), `--ceu-*` (light blue, arya concept), `--ouro-*` (gold, tierra concept), `--fogo-*` (flame red, fuego concept), `--ink` (near-black).
- Semantics: `--color-surface*`, `--color-text*`, `--color-border*`, `--color-action-primary*`, `--color-action-secondary*`, `--color-accent-concept*`, `--color-feedback*`.
- `data-concept` attribute scoping: `[data-concept="aqua|arya|tierra|fuego"]` remaps `--color-accent-concept`/`--color-accent-concept-soft` without touching any component CSS. Root default is "standard" (a neutral distinct from every concept).
- Rule: **components consume semantic tokens, never primitives** — with one known, disclosed exception (Section 10, technical debt): `footer.css`, `newsletter.css`, and `drawer.css` reference `--tatami-*`/`--lagoa-*` primitives directly for a couple of dark-surface tint steps that have no semantic alias yet. This is inherited verbatim from Claude Design's own source (its React components do the same inline), not something introduced locally — it's a legitimate gap to eventually close by adding the missing semantic aliases, not a bug to "fix" by guessing new values.

### Typography

See Section 7 in full — this is the most heavily audited layer in the project.

### Motion

Three duration roles (`--motion-feedback: 120ms`, `--motion-transition: 240ms`, `--motion-narrative: 480ms`) and two named easings (`--ease-out`, `--ease-in-out`) in `tokens/motion.css`. **Reduced motion collapses at the token level itself**, not as a per-component patch — under `prefers-reduced-motion: reduce`, all three durations become `0ms` and a global `*` rule forces `animation-duration`/`transition-duration` to `0.01ms`. `.tmk-reveal`/`.tmk-reveal-stagger` (`css/animations/reveal.css`) are the one sanctioned mechanism for narrative reveal; `js/animations/reveal.js` skips its `IntersectionObserver` entirely when reduced motion is active, rather than running it and relying on CSS alone. Component-owned keyframes (e.g. Drawer's slide-in animations) stay co-located in the component's own CSS file — `css/animations/` is reserved for motion shared *across* components, not fragmenting every component's own keyframes.

### Assets

- Fonts: self-hosted, WOFF2-first with TTF fallback (Section 7).
- Logo: **one** SVG artwork (`tmk_logo_black.svg`, WP attachment ID 8), inlined server-side via `inc/logo.php`'s `tmk_get_logo_svg_markup()`, recolored via `fill: currentColor` on its `.st0` path class (`css/components/logo.css`). This is why there's only one logo asset in active use despite a "black" and "white" SVG existing in Claude Design's asset list — both files are byte-identical with no embedded fill, meaning the *design's own intent* is a single artwork colored by context ("Black on the stage, white on interiors — never redrawn," per `guidelines/brand-logos.html`), not two separate drawings. **Do not reintroduce `<img src="...svg">` for the logo** — external SVG documents can't inherit page color, which is exactly the bug this fix corrects.
- Photography/illustrations: uploaded into the **WP media library** as real attachments, not duplicated inside the plugin. City interior photos (5, for Milano/Bologna/Roma/Lione/Rimini) are uploaded and linked via the `city` taxonomy's `hero_image_id` term meta.
- Garland illustration: uploaded (WP attachment ID 26), used in the Footer.

### Responsive strategy

Breakpoints are tokens, not per-component judgement calls: `tokens/layout.css` defines `--bp-tablet: 600px`, `--bp-desktop: 1024px`, `--bp-wide: 1440px` (mobile-first: mobile 0-599, tablet 600-1023, desktop 1024-1439, wide 1440+). `.tmk-mobile-only` (in `css/utilities/accessibility.css`) is the one sanctioned mobile/desktop visibility toggle class. **This has been verified correct by code review but not yet visually verified in a real browser at each breakpoint** — this is exactly the gap this handoff is meant to close (Section 12).

### Accessibility strategy

Semantic landmarks (`banner`/`contentinfo`/`complementary`/`main`), `aria-expanded`/`aria-current` on interactive nav elements, click-toggle mega menu (never hover-only, so it's keyboard-operable), sitewide `:focus-visible` ring (`--focus-ring`), a skip-link that now resolves correctly to a real `<main id="main">` (wrapped sitewide via `inc/accessibility-landmarks.php`'s `the_content` filter — fixed during Homepage construction). **Known, disclosed gaps, not yet closed:** no focus trap or focus-return on close for Drawer/Accordion/mega-menu overlays; color contrast has not been independently re-audited in this implementation phase (inherited from the original Design System Specification, presumed correct but unverified here).

### Performance strategy

WOFF2 fonts, two `<link rel="preload">` hints for the above-the-fold-critical weights (Londrina Solid Black, Basis Grotesque Regular), Elementor's Google Fonts CDN request eliminated entirely, dependency-ordered CSS/JS loading (no out-of-order requests), reduced-motion respected at both CSS and JS levels. **Not yet done, correctly deferred:** CSS/JS minification/concatenation, image lazy-loading strategy, any actual Core Web Vitals measurement (no browser tool was available to the outgoing session — this is squarely a task for the new Chrome-based session).

## 4. Elementor Strategy

**Stack:** Hello Elementor theme (unmodified) + Elementor Pro 4.2.0 + Elementor 4.2.0. Do not replace the theme, do not install an alternative page builder.

### Theme Builder

Header and Footer are real `elementor_library` Theme Builder templates:
- Header: post ID **25**, `_elementor_template_type = 'header'`.
- Footer: post ID **27**, `_elementor_template_type = 'footer'`.
- Both have display condition `include/general` (site-wide).

**Critical, hard-won lesson:** Elementor Pro caches which template applies where in a *separate* option, `elementor_pro_theme_builder_conditions`, managed by `ElementorPro\Modules\ThemeBuilder\Classes\Conditions_Cache`. Writing `_elementor_conditions` postmeta directly does **not** update this cache, and the template silently fails to render even though everything else looks correct. **Always set conditions via:**
```php
\ElementorPro\Modules\ThemeBuilder\Module::instance()->get_conditions_manager()->save_conditions( $post_id, array( array( 'include', 'general' ) ) );
```
This bug bit this project twice (once for the Header, once for the Footer) before the pattern above was locked in. Verify by checking `get_option('elementor_pro_theme_builder_conditions')` actually contains the new template's entry, not just that the postmeta was written.

### Header and Footer — current structure and its trade-off

Both templates are, today, literally:
```
Container (content_width: full)
  └── Shortcode widget → [tmk_header] / [tmk_footer]
```
This is **not visually editable inside Elementor** beyond deleting or repositioning the single shortcode block — every actual change (a nav label, a button color, a footer column) requires editing PHP. This was flagged explicitly to the user in an Elementor-implementation review (container hierarchy, nesting depth, global classes, maintainability inside the editor, editing experience for future designers) as a real gap against the stated goal that "every Elementor section must remain editable." **The user was informed and explicitly chose to accept this trade-off for Header/Footer rather than rebuild them.** Do not rebuild Header/Footer as a "fix" on your own initiative — that decision has already been made.

**The corrected pattern, adopted from the Homepage onward:** one real Elementor Container **per page section**, each containing exactly one narrowly-scoped shortcode for that section's content. The Homepage (Section 9) has 6 such containers (Hero, Narrative Band, City Cards, Trust Band, CTA Banner, Newsletter). This gives genuine section-level editability in Elementor — a designer can reorder, delete, duplicate, or restyle (padding/width/background) each section via Elementor's own Container settings — while the tested, pixel-faithful inner markup of each component stays PHP-rendered. **This is the standard to follow for every future page.** Default to a native Elementor Container per logical section; reserve the Shortcode widget inside it strictly for content that either (a) needs real WordPress data binding (a taxonomy/CPT loop Elementor's native widgets can't easily express) or (b) is a proven, already-correct shared component whose CSS assumes specific markup (rewriting it to be native-widget-agnostic is a larger, not-yet-attempted undertaking — see Section 10).

### Global Kit

Active Kit ID: **5**. Managed by `inc/elementor-kit.php`'s `tmk_ds_sync_elementor_kit()`:
- `system_colors` (4: primary/secondary/text/accent) + `custom_colors` (20, every semantic + concept + feedback role) mirrored from `tokens/colors.css`.
- `system_typography` (4) + `custom_typography` (7: H1-H4, body-small, caption, eyebrow) mirrored from `tokens/typography.css`.
- `default_generic_fonts = 'sans-serif'`.

**Known limitation:** this sync only runs on `register_activation_hook`. It is **not self-healing** — if the Kit is ever reset, replaced, or the site cloned, someone must manually re-trigger `tmk_ds_sync_elementor_kit()` (there is no admin button or WP-CLI command for this yet — see Section 10).

### Global Colors / Global Typography

Any **native** Elementor widget added anywhere on the site will see "TMK Voice," "TMK H1," the TMK color swatches, etc. in Elementor's own pickers — this works correctly today. It currently benefits nothing on Header/Footer (opaque shortcodes, invisible to Elementor's style panels) but will directly benefit every native Container/widget built from the Homepage onward.

### Reusable templates

Only the two Theme Builder singletons (Header, Footer) exist. **No Saved Template pattern library exists yet.** The moment a second page needs the same structural pattern (a Card grid layout, a CTA Banner section shell, etc.), extract it into a genuine Saved Template rather than duplicating the Container/shortcode structure by hand across pages.

### Global classes

Elementor 4.2's native "Global Classes" feature (`e_classes`) is **entirely unused** in this project. The `.tmk-*` class system is a real, consistent design system, but it lives in hand-written CSS/PHP, parallel to and invisible from Elementor's own Global Classes panel. This is fine for shortcode-rendered content; if you ever build genuinely native Elementor widget content, consider registering key classes (e.g. `tmk-cta`) as Elementor Global Classes so designers can apply them from the UI.

### Shortcode strategy

See the full list in Section 6. The governing rule: a shortcode is for (a) content that needs real WP data binding, or (b) an already-tested shared component whose markup/CSS pairing is proven correct. It is not a default fallback for "content I don't want to hand-build in Elementor's JSON."

### Editing philosophy

Prefer Flexbox Containers, Theme Builder, Global Colors/Fonts, Global Templates, and native CSS Classes over custom code. Only reach for custom CSS/JS/shortcodes when Elementor genuinely cannot reproduce the original behavior — real dynamic data binding is the clearest case; static content that a native Heading/Image/Button widget could handle is not.

## 6. Design System — every reusable component currently implemented

### CTA (`css/components/cta.css`)
**Purpose:** the one universal call-to-action button, used everywhere a link needs button styling.
**API:** class-based, not a shortcode — `<a class="tmk-cta tmk-cta--primary|secondary tmk-cta--sm|full">`.
**Variants:** `--primary` (filled, ember accent) / `--secondary` (ink outline). Size modifiers `--sm` / `--full` (full-width below tablet).
**States:** hover, active (via semantic action-state tokens), focus-visible ring inherited from base.
**Future usage:** every page will use this — booking CTAs, delivery CTAs, form submits.

### Accordion (`css/components/accordion.css` + `js/interactions/accordion.js`)
**Purpose:** shared disclosure pattern — currently the mobile nav's city list, designed to also serve FAQ blocks, job listing detail accordions, etc.
**API:** markup contract — a `[data-tmk-accordion]` group wrapper containing `.tmk-accordion-item` > `.tmk-accordion-trigger[aria-expanded]` + `.tmk-accordion-panel[hidden]` pairs.
**States:** single-open per group (closing others on open), `aria-expanded` reflects state.
**Future usage:** FAQ page/section, job listing detail, any future disclosure UI. **Do not write a new accordion script — reuse this one**, just wrap a new instance in its own `[data-tmk-accordion]` group.

### Drawer (`css/components/drawer.css` + `js/interactions/drawer.js`)
**Purpose:** shared off-canvas overlay — currently the mobile nav drawer, designed for reuse by e.g. a Filters panel.
**API:** `<aside data-tmk-drawer id="X">`, paired trigger `data-tmk-drawer-trigger="X"`, scrim `data-tmk-drawer-scrim="X"`, close button `data-tmk-drawer-close` (found via `closest()`, no id needed). Supports `--left`/`--right`/`--bottom` anchor modifiers.
**States:** open/closed (`hidden` attribute), Escape closes whichever drawer(s) are open, body scroll lock while open.
**Known gap:** no focus trap, no focus-return to the trigger on close (Section 10).

## 7. Typography System

**Two roles only:** Voice (**Londrina Solid**) for display/headline moments, Structure (**Basis Grotesque Arabic Pro**) for everything else — navigation, body, UI. This is explicit in Claude Design's own guideline cards (`guidelines/type-voice.html`, `guidelines/type-structure.html`).

### Weights (only request these — every other numeric weight has no matching `@font-face` and triggers browser synthetic-bold)

| Face | Weight | Token | Usage |
|---|---|---|---|
| Voice (Londrina Solid) | 900 | `--weight-voice` | Common — titles, H1-H4 |
| Voice | 400 | `--weight-voice-soft` | Common — accents, mobile nav links |
| Voice | 300 | (no token yet) | Rare, per guideline |
| Voice | 100 (Thin) | (no token, unused) | Shipped as an asset but not used by current design guidance |
| Structure (Basis Grotesque) | 400 | `--weight-structure` | Body text, default |
| Structure | 500 | `--weight-structure-medium` | Medium emphasis |
| Structure | 700 | `--weight-structure-bold` | Bold — CTAs, nav labels, eyebrows |

**No italic register exists anywhere in this system** — neither face ships an italic/oblique variant, and neither Claude Design guideline calls for one. Never set `font-style: italic` on either font role; without a matching `@font-face` the browser fakes a slant (synthetic oblique) which looks broken on both faces.

### Fallback stacks

```css
--font-voice: 'Londrina Solid', Impact, 'Arial Black', system-ui, sans-serif;
--font-structure: 'Basis Grotesque', 'Helvetica Neue', Arial, sans-serif;
```
Impact/Arial Black were deliberately added ahead of `system-ui` for Voice — they're near-universal on macOS/Windows and much closer in weight/width to Londrina Solid's black slab shapes, meaningfully reducing layout shift during the `font-display: swap` window versus a thin system sans fallback.

### WOFF2 strategy

All 9 font files (4 Londrina Solid + 5 Basis Grotesque) have a WOFF2 pair alongside the original TTF in `assets/fonts/`. Every `@font-face` in `tokens/fonts.css` lists WOFF2 first (`format('woff2')`), TTF as a fallback `src` (`format('truetype')`) for any engine that can't parse WOFF2 — effectively none of this project's real targets, but the fallback costs nothing. `font-display: swap` throughout. WOFF2 files are ~25-27% the size of their TTF originals.

### Asset integrity notes — read this before touching any large Claude Design asset

**There was a significant misdiagnosis in this project that was later corrected — know the real story:**

1. Three Basis Grotesque TTFs (Regular, Light, Medium) were found truncated — their table directory pointed past the actual file length, corrupting the tail of the GPOS (kerning) table and losing the trailing FFTM table.
2. This was **initially misdiagnosed** as a Claude Design source-asset defect, "confirmed" by re-fetching the file and seeing the same truncation.
3. **The re-fetch used the same tool call that caused the problem in the first place.** The actual cause: `DesignSync get_file` is capped at **256 KiB of base64-encoded content**, which decodes to exactly **196,608 bytes (192 KiB)** of real binary data. Any file whose true decoded size exceeds that is silently truncated at exactly 196,608 bytes — and the tool response **does** self-report this via a `"truncated": true` field that was not checked.
4. The same 192 KiB truncation was independently caught on `hero-cluster.png` (the Homepage's hero illustration) — also exactly 196,608 bytes, also `"truncated": true`. This time the field was checked, and the correction above was made immediately.
5. **The complete original font files almost certainly exist, untouched, in Claude Design.** They were simply never fully retrieved. The interim fix in place — dropping only the two provably-truncated tables (GPOS, FFTM) and re-saving — is a real, working, non-fabricated repair (no glyph/metric/hinting data was invented), but it does mean Basis Grotesque Regular/Light/Medium currently render **without fine OpenType kerning pairs** until the true, complete files are obtained.
6. `hero-cluster.png` **could not be repaired the same way** — a truncated PNG IDAT stream is missing actual pixel data, not a droppable metadata tail. It has **not** been uploaded. The Homepage's Hero currently renders without its illustration.
7. The user chose to export/share the complete files directly rather than have the outgoing session work around the cap. **As of this handoff, whether those files have been received is unknown to this document — check for them before assuming either state.** If they've arrived: replace the 3 TTFs in `assets/fonts/`, re-run the WOFF2 generation (fontTools, `TTFont(path, lazy=False)` → `.flavor = "woff2"` → `.save()`), update `tokens/fonts.css`'s integrity-note comment, upload `hero-cluster.png` to the media library, and wire its attachment ID into the Homepage's `[tmk_hero]` shortcode's `media_id` attribute.

**The one rule that must never be broken again: check the `truncated` field on every `DesignSync get_file` call for a binary or otherwise large asset, before doing anything else with the response.** If `truncated: true`, the content you have is incomplete — do not analyze it, do not "fix" it as if it were a source defect, escalate immediately.

### Google Fonts decision

Elementor unconditionally scans every control of type `FONT` during CSS compilation (`core/files/css/base.php` line ~493-494, `add_font()`) and checks the font name against its own catalog (`includes/fonts.php`) **regardless of whether that control was authored as "custom" or "google" in the editor**. "Londrina Solid" happens to be a real Google Fonts family name. Without intervention, Elementor would print a live `fonts.googleapis.com` request for it on every page load — Google's hosted version only ships weight 400, directly conflicting with this project's self-hosted 100/300/400/900, plus an avoidable third-party request (GDPR-relevant for an EU business) for a font already served locally.

**Fix applied:** `elementor_google_font` option forced to `'0'` (`tmk_ds_disable_elementor_google_fonts()` in `inc/elementor-kit.php`, called from `tmk_ds_sync_elementor_kit()`). This is a root-cause, sitewide fix — Google Fonts should never load in this project, for this family or any future one — not a per-font-name patch. Verified live: zero `fonts.googleapis.com`/`fonts.gstatic.com` references on the rendered page.

## 8. Decisions Made — chronological log

**Format:** problem → chosen solution → reason → expected long-term benefit.

1. **No WP-CLI available in this environment.**
   → Bootstrap every WordPress-side script via a direct `wp-load.php` require, run through Local's bundled PHP CLI binary with explicit `-d mysqli.default_socket=...` / `-d pdo_mysql.default_socket=...` flags (Local's PHP CLI doesn't share php-fpm's socket config by default).
   → This was the only reliable way to run WP-aware PHP headlessly in this environment.
   → Standing technical approach for any future WP-side scripting in this project; the exact socket path is in the conversation history and can be re-derived via `find "...Local/run" -iname mysqld.sock`.

2. **Content modeling needed a mechanism, and ACF Pro wasn't explicitly authorized.**
   → Used native `register_post_type`/`register_taxonomy`/`register_post_meta`/`register_term_meta` instead of ACF.
   → IA §36 said "ACF Pro or equivalent" and left the mechanism open; adding a new paid third-party plugin dependency without authorization would have been overstepping.
   → No ACF dependency for the life of the project; all content fields are REST-exposed and Elementor Dynamic Tag compatible natively.

3. **Elementor Theme Builder template wasn't rendering despite correct-looking postmeta.**
   → Discovered `elementor_pro_theme_builder_conditions` is a separate cache, only rebuilt by `Conditions_Manager::save_conditions()`.
   → Raw `update_post_meta('_elementor_conditions', ...)` bypasses this cache entirely.
   → Documented as a hard rule (Section 4) — this class of bug is now impossible to reintroduce if the rule is followed.

4. **Risk of TMK documentation overriding an already-approved Claude Design decision (Job Application CV field).**
   → User issued an explicit, strict three-tier priority order: Claude Design > TMK docs > engineering judgement.
   → The docs describe intent, not the final approved pixel/interaction reality, which had since evolved in Claude Design.
   → Prevents an entire class of "faithful to the wrong source" bugs for the rest of the project (Section 2).

5. **CTA/Accordion/Drawer styles were embedded inline inside `header.css`, discovered right after the "systems before pages" mandate.**
   → Extracted into their own `css/components/*.css` files; `header.css` now contains only Header-specific rules.
   → Caught as a direct violation of the user's own explicit rule ("if you notice yourself copying styles between pages, stop and move that styling into the global system first") — the violation was single-file premature commitment, not literal duplication, but the same anti-pattern.
   → Established the components-vs-layout file separation that the later full reorg (#9) formalized.

6. **Two logo SVG files (black/white) were byte-identical with no embedded fill — ambiguous which to use where.**
   → Inlined the single SVG server-side and recolor via `fill: currentColor` on its unstyled `.st0` path class; removed the false premise of "two logos."
   → The SVGs' own structure (no embedded fill, shared class) plus Claude Design's own guideline ("never redrawn") both point to one artwork recolored by context, not two drawings.
   → One logo asset to maintain forever; correct color in Header (light stage) and Footer (dark) automatically via CSS inheritance, no per-context asset swapping.

7. **Newsletter signups needed a real backend, not a fake success message.**
   → Built a real AJAX endpoint + a dedicated `newsletter_sub` CPT (private posts, email as title).
   → "Production-ready" should mean actually functional, with an explicit placeholder marked for the eventual real CRM/ESP integration IA §39 leaves open — not a demo that silently does nothing.
   → Real subscriber data exists as soon as the site launches, even before Brevo/similar is wired in.

8. **The newsletter CPT slug `newsletter_subscriber` (21 chars) caused every signup to fail silently (`success: true` returned regardless).**
   → Renamed to `newsletter_sub` (14 chars).
   → WordPress's `wp_posts.post_type` column is `varchar(20)`; anything longer causes `wp_insert_post` to fail with a DB error that the AJAX handler wasn't checking for.
   → Documented as a hard constraint (Section 11) — always keep custom post type slugs ≤ 20 characters, and verify inserts actually succeeded in the database, not just that the handler returned success.

9. **User mandated a full architectural reorganization: base/tokens/utilities/animations/components/layout/pages (CSS) and animations/interactions/navigation/components (JS).**
   → Executed exactly as specified; split the monolithic `header.js` into `mega-menu.js` (navigation), `drawer.js` + `accordion.js` (interactions, genericized to support multiple independent instances), moved header/footer CSS into `css/layout/`, extracted `.tmk-container` classes out of the `tokens/layout.css` token file into `css/layout/container.css`.
   → Explicit user requirement, matching real anti-patterns already caught (inline component styles, header-scoped "generic" JS).
   → This is the architecture Section 3 describes — it is considered stable and is not expected to change again (Section 11).

10. **Elementor was silently double-loading "Londrina Solid" from Google's CDN.**
    → Disabled Elementor's Google Fonts loading entirely at the `elementor_google_font` option (root cause), verified by reading Elementor's own source rather than guessing.
    → A per-font-name workaround would only fix today's known collision; a fully self-hosted, closed design system should never talk to Google Fonts for any font, present or future.
    → Zero external font requests, permanently, regardless of what font names Elementor's catalog grows to include later.

11. **Typography needed a full rigor pass (explicit user request).**
    → WOFF2 conversion for all 9 fonts, weight-discipline documentation, improved Voice fallback stack, replaced ~9 hardcoded `font-weight` numbers with the semantic tokens that already existed for them.
    → Matches "treat typography with the same rigor as tokens and components."
    → A typography layer that's internally consistent and self-documenting for future contributors.

12. **The font-truncation misdiagnosis (see Section 7 in full) and its correction.**
    → Corrected the `fonts.css` documentation comment to attribute the truncation to the retrieval tool's cap, not a Claude Design source defect; established the "always check `truncated`" rule.
    → Intellectual honesty — the original claim was wrong and re-asserting it would have misled every future session (including this one) about where the real problem lives.
    → Prevents repeating the same misdiagnosis on `hero-cluster.png` or any future large asset — which is exactly what happened next, and this time was caught correctly.

13. **Elementor-side review found Header/Footer are not editable inside the visual editor.**
    → Flagged explicitly with full detail (container hierarchy, global classes, editing experience); user was given a 3-way choice (rebuild now / accept trade-off / partial fix) and **explicitly chose to accept the trade-off** for Header/Footer specifically.
    → Header/Footer already work correctly and rebuilding them is real, nontrivial effort; the user's call, once informed, is authoritative.
    → Going forward, the corrected "one Container per section" pattern (Section 4) is used for every new page starting with the Homepage, so this trade-off is not silently repeated everywhere by default.

14. **The skip-link (`href="#main"`) had no matching `id="main"` anywhere, flagged in the Production Readiness Declaration.**
    → Fixed systemically via a `the_content` filter (`inc/accessibility-landmarks.php`) that wraps singular page content in `<main id="main">`, scoped to `is_page() && is_main_query() && in_the_loop()` so it applies to every future page automatically without a theme edit or a per-page fix.
    → A foundation-level accessibility gap deserves a foundation-level fix, not a one-off patch on whichever page happened to be built first.
    → Every future page gets a working skip-link target for free.

15. **The Homepage's "Le città" section needed real data, and Claude Design's own demo array (`data.js`) is illustrative, not a data source.**
    → Built `tmk_render_city_card()`/`[tmk_city_cards]` against the real `city` taxonomy (photo via `hero_image_id` term meta, count via the term's real `location` post count, href computed from real permalinks), reproducing Claude Design's exact 5-city selection and order but with live counts (e.g. Milano correctly shows 5 ristoranti, not the demo's placeholder 4).
    → Priority 1 governs the Homepage's *layout and behavior*, not literal reproduction of placeholder numbers that don't match the real seeded content.
    → The Homepage will stay correct automatically as locations are added/removed in WordPress, with zero future edits to the page itself.

## 11. Rules For Future Development

These are immutable. Do not violate them without the user's explicit, in-the-moment approval — and if you get that approval, log the exception in Section 8's format.

1. **Never redesign. Never reinterpret.** Translate Claude Design's approved implementation; don't improve on it, simplify it, or "fix" its design decisions.
2. **Follow the three-tier source-of-truth order, always:** Claude Design > TMK docs > engineering judgement (Section 2).
3. **Never bypass design tokens.** Every color, spacing value, typography role, radius, shadow, and duration must come from `css/tokens/*.css`. If a value you need doesn't exist as a token, that's a signal to check Claude Design's actual token files again, not to hardcode a number.
4. **Never hardcode colors.** Always `var(--color-*)` (semantic) or, where a semantic alias genuinely doesn't exist yet and Claude Design's own source doesn't use one either, the closest primitive with a comment explaining why.
5. **Never hardcode spacing.** Always `var(--space-*)`.
6. **Never hardcode font-weight numbers** where a semantic `--weight-*` token exists for that exact value (Section 7).
7. **Always build genuinely reusable pieces as components** (`css/components/` + `inc/*-render.php`), not page-specific one-offs. Before creating any new CSS/JS file, ask which layer it belongs to (tokens/base/utilities/animations/components/layout/pages) — the docblock in `inc/enqueue.php` is the reference.
8. **Always keep Claude Design as the visual source of truth** — re-fetch it fresh for each page/component rather than relying on a previous session's memory of it, since the project can change between sessions.
9. **No architectural refactoring without explicit approval.** The layer hierarchy, dependency chain, and enqueue mechanism (Section 3) are locked. Adding a new component/page file into the existing structure is normal work, not refactoring; changing the structure itself is.

## 14. Homepage Audit — Implementation Log (2026-07-29, plugin 1.4.0)

First session with a real browser. Full visual/technical audit of the Homepage at 375 / 1023 /
1024 / 1440 px viewports, plus hover, focus, keyboard, landmark, motion, network and image
checks. Format follows Section 8: problem -> chosen solution -> reason -> long-term benefit.

### Fixed

1. **THE ROOT-CAUSE BUG: the whole design system was losing every cascade tie.**
   The TMK chain was enqueued on `wp_enqueue_scripts` at priority **5**, i.e. BEFORE the theme.
   Hello Elementor's `assets/css/reset.css` (priority 10) resets `body{background-color:#fff;
   color:#333;font-family:<system sans>}` and `h1..h6{font-family:inherit;font-weight:500}` with
   bare element selectors, so it beat `css/base/base.css` on source order every time. Live
   result: the entire site rendered in the system sans at weight 500 on a white background -
   no Londrina Solid, no Basis Grotesque, no --color-surface - even though the tokens were all
   correct and all 24 stylesheets were loading with HTTP 200.
   -> Moved the hook to priority **20** (inc/enqueue.php). The chain's internal order is
   unchanged; it is guaranteed by the wp_register_style dependency graph, not by this priority.
   -> Verified: TMK now prints after reset.css / theme.css / frontend.min.css / the Kit CSS, and
   equal-specificity ties resolve in the design system's favour, which is the correct outcome
   for a design system.
   -> Every subsequent fix in this list was previously masked by this one.

2. **Trust Band sat flush-left instead of centred.** `.tmk-trust-band` declares
   `margin-inline:auto`, but Elementor's frontend.min.css ships
   `.elementor .elementor-widget:not(...):not(...) figure{margin:0}` at specificity (0,4,1) for
   its own Image widget, which silently defeated it because the component root is a semantic
   <figure>.
   -> Re-asserted the component's own declared intent at matching specificity in
   trust-band.css. The <figure>/<blockquote>/<figcaption> semantics are unchanged.

3. **Trust Band attribution rendered in synthetic italic**, violating the absolute no-italic
   rule in Section 7 (neither type role ships an oblique face). Source: Hello Elementor's
   reset.css `figcaption{font-style:italic}`.
   -> Normalised in the base layer: `figcaption,cite,address,dfn,var{font-style:normal}`, so no
   component ever has to patch it and no future page can reintroduce it.
   -> `em`/`i` deliberately left alone: suppressing content-level emphasis is a design
   decision, not a bug fix. Flagged for Claude Design review.

4. **Horizontal page overflow at mobile (document 483px wide inside a 375px viewport).**
   `.tmk-card--overlay` pairs `min-height:180px` with `aspect-ratio`. Once min-height clamps the
   block size it becomes definite, so the browser derives the INLINE size from the ratio:
   180 x 21/8 = 472.5px, on a 340px grid track.
   -> `max-width:100%` on `.tmk-card--overlay`, which is what makes the min-height floor behave
   as intended instead of blowing out the layout. Documented as load-bearing in card.css.

5. **The mobile hamburger was visible on desktop, next to the full desktop nav.**
   `.tmk-mobile-only{display:none}` lives in the `utilities` layer, which the enforced chain
   loads BEFORE `components`/`layout`, so `.tmk-icon-btn{display:flex}` in css/layout/header.css
   won the equal-specificity tie. A utility that cannot win is not a utility.
   -> `!important` on both branches of `.tmk-mobile-only`, documented as deliberate.
   -> IMPORTANT follow-up caught in the same session: the first version of this fix broke the
   mobile Drawer, because `.tmk-mobile-only` is also on the drawer, whose open/closed state IS
   the `hidden` attribute (`.tmk-drawer[hidden]{display:none}`) - !important outranked it and
   pinned the drawer permanently open below 1024px. Final form uses
   `.tmk-mobile-only:not([hidden])` for the visible branch, so drawer.css keeps full control of
   state while the utility governs only which viewports the element exists in.
   -> The clean structural fix is to move `utilities` to the END of the layer chain. That is an
   architectural change to a locked order (Rule 9) and needs sign-off - NOT done.

6. **Two `main`, two `banner` and two `contentinfo` landmarks; two skip links.**
   Elementor Pro's Theme Builder already wraps header/footer documents in its own <header> and
   <footer> elements, and Hello Elementor's page template already emits
   <main id="content">. On top of that the plugin added `<header role="banner">`,
   `<footer role="contentinfo">` and `<main id="main">`, and Hello printed its own English
   "Skip to content" alongside the designed Italian "Vai al contenuto".
   -> inc/header-render.php and inc/footer-render.php now render `<div class="tmk-header">` /
   `<div class="tmk-footer">` (pure style hooks); the landmarks are owned by Elementor's
   wrappers, which ARE the faithful equivalent of Claude Design's own top-level header/footer.
   -> inc/accessibility-landmarks.php now wraps content in `<div id="main" tabindex="-1">`
   instead of a nested <main>. The skip-link target still resolves; the landmark is the theme's.
   This refines decision 8.14 rather than reversing it - the goal (a real skip-link target) is
   still met, without the invalid nesting.
   -> Hello's duplicate skip link disabled via its own settings screen (Hello > Settings > SEO
   and accessibility > "Disable skip links"), whose own tip recommends exactly this when a
   plugin already provides one. No theme file touched (Rule 14).
   -> Result: exactly one banner, one main, one contentinfo, one skip link.

7. **The theme's page title ("Home") rendered above the Hero on every page.**
   -> Disabled sitewide via Hello > Settings > Structure and layout > "Hide page title" (an
   option, not a theme edit), so every future TMK page inherits it. See open issue A: the page
   now has NO h1 at all until the Hero gets its headline.

8. **Card media shipped as a bare `<img src>` at the hardcoded 'large' size:** no srcset, no
   sizes, no width/height, no lazy loading, and permanently upscaled (1024px file rendered at
   1140px, up to 1416px before fix 10 below).

   `sizes` hint, so the card inherits WordPress' own responsive-image pipeline: 4 srcset
   candidates, intrinsic width/height for CLS, `decoding="async"`, empty alt (correct - the
   accessible name comes from the card's own title/eyebrow inside the same link).
   -> Added a `loading` shortcode attribute (default 'lazy'); `tmk_render_city_cards()` marks

9. **The mobile-nav trigger exposed no state to assistive technology** (`aria-expanded` absent
   entirely), contradicting Section 3's own accessibility strategy.
   -> Added `aria-expanded="false"` + `aria-controls` to the markup, and generic

   in the generic interactions layer, so every future Drawer instance (Filters, mobile cart)

### Fixes applied

**FIX 15 - CTA auto-full-width fired at the wrong breakpoint (`css/components/cta.css`).**
Problem: the rule was authored as `@media (max-width: 1023px) { .tmk-cta:not(.tmk-cta--sm) }`,
i.e. the *desktop* bound, while its own comment said "Below tablet" and Section 3 defines
mobile 0-599 / tablet 600-1023 / desktop 1024-1439 / wide 1440+. Measured consequence at a 1023px
viewport: the Homepage Hero CTA rendered **960px wide** - a full-viewport slab, not a button.
Chosen solution: `max-width: 599px`, the real "below tablet" bound. Reason: the file's own comment
and the token breakpoint naming both say below-tablet; touch-target compliance comes from the
13px/28px padding, never from `width:100%`; and `.tmk-cta--full` exists precisely so instances that
genuinely need full width opt in explicitly. Verified: 375 -> 312px (full), 599 -> 536px (full),
600 -> 153px (intrinsic), 1023 -> 153px, 1024 -> 153px, 1440 -> 153px. Long-term benefit: the one
global CTA rule now switches at the same width as every other breakpoint in the system.

**FIX 16 - Homepage Newsletter section was flush-left in a 1140px container (Elementor, page 36).**
Problem: `.tmk-newsletter` is `max-width:480px` with no auto margin (correct - that is the direct
translation of NewsletterCapture.jsx, which is also used inside a Footer column). Section 6's
container already had `flex_justify_content: center` saved by its author, but on a column-direction
flex container that centres along the *vertical* main axis and does nothing horizontally, so the
480px block sat hard left with ~660px of dead space to its right. Chosen solution: set the
container's **Align Items: Center** (`flex_align_items`) in the Elementor editor - the cross-axis
control, which is the one that actually centres it. Reason: the intent was already recorded in the
page data; this fixes the axis, it does not invent a layout. It is also page-level layout, which per
Rule 15 belongs on the Elementor Container, not in the shared component CSS. Verified: block centre
713px in a 1425px viewport, and centred at 375/599/600/1023/1024/1440. Long-term benefit: the
Newsletter component stays reusable in a left-aligned Footer column without a page-specific override.

**FIX 17 - Elementor's breakpoints did not match the design system's breakpoints (Elementor Kit 5).**
Problem: `hasCustomBreakpoints` was false, so Elementor was switching at its defaults - mobile
max-width 767, tablet max-width 1024 - while every TMK media query switches at 599/1023/1440. Two
competing responsive systems in one site. Worst case was the exact 1024px viewport, where Elementor
still applied *tablet* styles while the design system had already applied *desktop* styles. Chosen
solution: Site Settings > Layout > Breakpoints set to Mobile Portrait **599** and Tablet Portrait
**1023**. Reason: Section 3 already declares breakpoints to be tokens rather than per-component
judgement calls, and Section 4 already establishes that the Kit is meant to mirror the design
system's tokens - this completes that mirror rather than changing any architecture. Risk at the time
of the change was nil: no responsive control is set on any native widget anywhere on the site yet
(Header/Footer are single opaque shortcodes, and the Homepage's six containers only set
content_width / padding / flex alignment). Verified live:
`elementorFrontendConfig.responsive.breakpoints.mobile.value === 599`, `.tablet.value === 1023`,
`hasCustomBreakpoints === true`; hamburger still appears at <=1023 and the desktop nav at >=1024;
no horizontal overflow at any of 375/599/600/1023/1024/1440. Long-term benefit: from Menu Hub
onward, any responsive value a builder sets in Elementor lands on exactly the same pixel boundary
as the CSS, so the two systems can never disagree again.

**ARCHITECTURAL FOLLOW-UP for FIX 17:** `tmk_ds_sync_elementor_kit()` in `inc/elementor-kit.php`
mirrors colours and typography into the Kit but says nothing about breakpoints, so the 599/1023
values above are currently a manual, hand-made setting that a Kit reset would silently revert to
767/1024. When the self-healing sync trigger in Section 10 is built, teach it to write
`viewport_mobile: 599` / `viewport_tablet: 1023` from `tokens/layout.css` as well.

**FIX 18 - Mega menu: aria-controls wired + focus-return on close**
(`inc/header-render.php`, `js/navigation/mega-menu.js`).
Problem: the mega trigger carried `aria-expanded` but no `aria-controls`, and the panel had no id,
so assistive tech could not associate the two; and `close()` hid the panel without moving focus, so
Escape or a click-outside while focus sat on a city link inside the panel orphaned focus on a hidden
node and the browser silently reset it to <body>. Chosen solution: `id="tmk-megamenu"` on the panel,
`aria-controls="tmk-megamenu"` on the trigger, and a `close()` that captures
`mega.contains(document.activeElement)` before hiding and returns focus to the trigger only if focus
was genuinely inside. Reason: this closes the mega-menu half of the focus-return gap disclosed in
Section 10 (the Drawer half was closed in session 1), and it mirrors the treatment already applied
to the Drawer, so both header overlays now behave identically. Verified: Escape from a link inside
the panel leaves `hidden === true`, `aria-expanded === "false"` and
`document.activeElement === trigger`. Drawer re-tested for regression: opens to 330px, locks body
scroll, moves focus in, Escape closes, focus returns, `aria-expanded` flips correctly.

   citta, zero compromessi." cta_label="Prenota ora"]`. `hero-render.php` already supports
   `headline`, `eyebrow`, `concept_label` and `media_id`, and `hero.css` already styles
   `.tmk-hero--contained h1 { max-width: 720px }`. Copy is the one thing that must never be invented.
3. **H1 strategy - the Homepage currently has ZERO `<h1>`.** This follows directly from item 2. The
   heading outline is H3 x7 (mega-menu city columns), H2 (Narrative Band), H2 (CTA Banner), H3
   (Newsletter), H3 x4 (Footer). Hello Elementor's `h1.entry-title` ("Home") was deliberately hidden
   in session 1 because the Hero is the page's title moment. Three candidate resolutions, in
   preference order: (a) the Hero receives its real `headline` from Claude Design - correct, and
   fixes the outline for free; (b) if Homepage.jsx's Hero genuinely carries no text headline because
   the wordmark lives inside `hero-cluster.png`, then the h1 must be a visually-hidden one carrying

4. **Narrative reveal animations - the mechanism is complete but nothing consumes it.** `reveal.css`
   + `reveal.js` are correct, IntersectionObserver-driven, reduced-motion-aware at both the token
   level and via a belt-and-braces `@media` override, and they stagger children with
   `calc(min(var(--tmk-stagger-i,0),8) * 60ms)`. But there are **zero** `.tmk-reveal` /

   `narrative-band-render.php` and `card-render.php` contain no reveal logic at all. `reveal.css`'s
   own comments say the stagger is "used by Card Grid, Trust Band rotating items" and the reveal is
   "for Arrival/Content-stage sections", which is a strong hint that the classes are applied at the
   *page* level in Claude Design (Homepage.jsx wrapping its sections) rather than inside components.
   WHICH sections animate, in what order, is a motion-design decision. Guessing it would be exactly
   the "invent animations" failure the brief forbids. Needs Homepage.jsx.
5. **Section-to-section vertical rhythm.** Measured with the page open: every one of the six
   Elementor containers has zero vertical padding, so the only vertical space between sections is
   whatever each component self-pads plus Elementor's default 10px `.e-con-inner` padding. Result:
   Hero 48/48, Narrative Band 0/0, City Cards 0/0, Trust Band 32/32, CTA Banner 64/64, Newsletter

   double it up on Hero / Trust Band / CTA Banner; and the tight gaps fall exactly where the adjacent
   component self-pads 0, which may well be intentional (a Narrative Band flowing straight into the
   card river). Unlike FIX 15 and FIX 16 there is no internal evidence that the current state
   contradicts anyone's stated intent, so this one genuinely needs Homepage.jsx.

### New architectural knowledge discovered this session

- **Elementor's breakpoints are now custom (599 / 1023) and match `tokens/layout.css`.** See FIX 17
  and its follow-up. This is the one genuinely new architectural fact in this session.
- **The `stack` and `inset` role tier of the spacing token system is defined but entirely unused.**
  `tokens/spacing.css` declares `--space-stack-sm/md/lg`, `--space-stack-section`
  (`clamp(var(--space-8), 8vw, var(--space-10))`, i.e. 64-128px) and `--space-inset-sm/md/lg/xl`,
  and the file header assigns them roles ("inset = inside a component, stack = vertical between
  siblings/sections"). Grepping every component, layout, base and utility stylesheet: **not one of
  them is consumed anywhere.** Components reach past the role layer straight to the raw
  `--space-1..10` steps. That is not wrong per Rules 4-6 (they are still tokens, not magic numbers),
  but the semantic tier is dead weight today, and `--space-stack-section` in particular is the
  obvious candidate for the open question in item 5 above - which is why item 5 is a question about
  Claude Design rather than a free choice.
- **`--bp-tablet` (600px) and `--bp-wide` (1440px) are still unreferenced by any media query.** After
  FIX 15 the only real media queries in the system are `max-width: 1023px` (accessibility.css,
  header.css, cta-banner.css), the new `max-width: 599px` (cta.css) and
  `prefers-reduced-motion: reduce`. The system is effectively two-breakpoint in practice. That is
  fine and should stay fine - do not add wide-viewport rules speculatively.
- **`elementor-icons-css` is admin-bar-only on this site.** The only elements resolving to the
  `eicons` family are the WP admin bar's `.ab-item` links, and the stylesheet is absent from the
  logged-out document. Do not spend a perf ticket on it.
- **Markup validity note, flagged not fixed:** the Trust Band renders
  `<figure><div class="tmk-trust-band__item"><blockquote/><figcaption/></div>...</figure>`.
  `<figcaption>` must be the first or last child of its `<figure>`, so this nesting is invalid HTML.
  It is a faithful translation of TrustBand.jsx and the caption is still announced, so the
  accessibility impact is nil. Changing `figure` -> `div` would also break the Elementor interop rule
  from session 1 (`.elementor .elementor-widget .elementor-shortcode > figure.tmk-trust-band`) that
  exists purely to defeat Elementor's `figure { margin: 0 }`. Raise it with Claude Design rather than
  unilaterally re-tagging it.
- **Component-internal hardcoded values, flagged not fixed:** control paddings (`13px 28px` on
  `.tmk-cta`, `12px 14px` on `.tmk-newsletter__input`, `16px` in accordion.css, `10px` in
  accessibility.css) and three overlay alphas (`rgba(36,28,19,.06)` / `.12` CTA hover washes,
  `rgba(20,14,8,.30)` drawer scrim, `rgba(253,251,245,.06)` footer input fill) sit outside the token
  system. These are off-scale by nature - optical control padding does not land on a 4px stack, and
  the alphas would each need a new semantic token to be expressible. Both are the same class of
  disclosed debt as the `--tatami-*` primitive references already recorded in Section 10. Tokenising
  them would change rendered output, so it must not happen without Claude Design.

### 17.4 New architectural knowledge discovered this session

- **ELEMENTOR'S ELEMENT CACHE IS ON, WITH A 24-HOUR TTL** (`elementor_element_cache_ttl = 24`,
  Elementor > Settings > Performance). This is the single most important operational fact learned
  this session. Elementor serves **pre-rendered element markup** from cache, so a change written
  to `_elementor_data` from anywhere other than the Elementor editor - the REST API, a direct DB
  write, WP-CLI - is stored correctly and **does not appear on the front end at all**. It looks
  exactly like a failed save. The DB was verified to hold the new data while the front end still
  rendered the old markup.
  **The fix is Elementor > Tools > Clear Files & Data after every out-of-editor page edit.**
  Do not "fix" this by disabling Element Cache; it is a site performance setting the user owns.
  This almost certainly explains any past impression that a page edit "did not stick".
- **Editing page 36's structure from outside Elementor works and is much faster than the editor
  UI:** GET `/wp-json/wp/v2/pages/36?context=edit` with an `X-WP-Nonce`, mutate the parsed
  `meta._elementor_data`, POST it back to the same route, then clear Elementor's cache as above.
  `_elementor_data` is REST-writable on this install. Verified round-trip byte-identical.
- **`elementor_optimized_image_loading = 1`** - Elementor applies its own `fetchpriority="high"`
  to what it believes is the LCP image and `loading="lazy"` below the fold. Our Hero now declares
  both explicitly, which is the stronger signal and avoids depending on Elementor's guess; keep
  that in mind before adding competing hints elsewhere.
- **The 1140 vs 1280 width split is now visible on the page.** The city stack is
  `--container-wide` (1280) per the source, while the Trust Band, CTA Banner and Newsletter
  sections are still inside Elementor's 1140px boxed containers. That is a real, deliberate
  intermediate state, not an oversight: unifying it is part of the pending restructure (D9/D10)
  which is blocked on C7. Do not "fix" one section's width in isolation.
- **css/components/card.css now carries page-level CSS it should not own.** `.tmk-city-bands*`
  belongs in css/pages/homepage.css with its handle in `tmk_ds_page_handles()`. It lives in the
  component file solely because the Plugin File Editor cannot create files. Both blocks are

## 18. Production Polish - Session 5 (Chrome session, 2026-07-29, plugin 1.5.0 -> 1.5.2)

### 18.1 The brief changed, and so did the standard of correctness

Sessions 1-4 were held to pixel fidelity against Claude Design. From this session the user's
instruction is different and explicit: **the objective is no longer pixel-perfect fidelity, it is
the best possible production implementation.** Spacing, vertical rhythm, typography, button
sizing, hover states, interaction quality, transitions, micro-animations, image composition,
visual hierarchy, responsive behaviour, accessibility, perceived performance and conversion
quality are all explicitly open to senior judgement. What must NOT change: the design language,

structure before extending it.

Practical consequence for future sessions: Rule 1 ('never redesign, never reinterpret') is now
scoped to design LANGUAGE and IA, not to every measurement. A defect is a defect even when it is
a faithful translation - but a faithful translation is not a defect merely because a better
arrangement exists. Fix things that are wrong; do not restyle things that are merely different.

### 18.3 Fixes applied this session (format: problem -> solution -> reason -> long-term benefit)

**FIX 27 - Two city cards rendered LITERALLY INVISIBLE text (css/components/card.css).**
Problem: Reggio Calabria and Capo d'Orlando have no hero_image_id, so Card's overlay shape
rendered an empty .tmk-card__media and the only thing behind its --tatami-50 Voice title was the
card's own cream --color-surface-raised. Measured: **title 1.00:1, eyebrow 1.21:1** - not merely
low contrast, invisible. The scrim cannot rescue it: it is built to darken a PHOTOGRAPH, and a
0.55 ink wash over cream is still a light ground (122,116,107 - 4.47:1 title / 3.70:1 eyebrow,
still an AA failure at 12px).
-> .tmk-card--overlay:not(:has(.tmk-card__media)){background:var(--color-surface-inverse)}.
-> Restores exactly the condition the scrim and the light title already assume - dark ground,
light type - using the surface token the CTA Banner and Footer already stand on, so a photo-less
city reads as a deliberate ink tile rather than a broken card. Measured after: title 14.6:1,
eyebrow 11.9:1. Written with :has() rather than a PHP modifier class so it protects EVERY caller
of Card, including future ones that forget to pass media, with no change to the render contract.
-> Any city, location or concept added without photography now degrades gracefully instead of
shipping unreadable text. This is the class of bug that only a real browser can find.

**FIX 28 - Every restaurant card was serving a photograph upscaled 1.61x, and downloading the
same photograph twice (inc/media.php + inc/card-render.php).**
Problem, two layers deep. (a) WordPress 6.7+ prepends sizes="auto" to lazy images; per spec auto
as the first entry makes the browser IGNORE the rest of the list and select from srcset using the
rendered LAYOUT width. (b) Card's overlay shapes crop a wide photo into a much taller box with
object-fit:cover, so the layout WIDTH understates the resolution the visible crop needs. Measured:
a 286x214 location card, fed the city's 1180x550 banner, was served the 300x140 crop and upscaled
it 1.61x vertically - visibly soft photography on every restaurant card, while a perfectly good
768w candidate sat unused in the same srcset.
-> add_filter('wp_img_tag_add_auto_sizes','__return_false') in inc/media.php, so each component's
deliberate, hand-computed hint is the authority again; and $row_sizes in tmk_render_city_bands()
changed to the city banner's OWN hint, '(min-width: 1280px) 1216px, calc(100vw - 64px)'.
-> The second half is the interesting one. Every location card in a block is fed that block's city
photograph (media={c.img} in Homepage.jsx), so card and banner are literally the same file.
Requesting the same candidate makes the whole restaurant row resolve to the banner's
already-downloaded, already-decoded bitmap: one HTTP request and one decode serve the band and all
of its cards. Measured: interior-roma.jpg was fetched twice, full 125KB + 768w 59KB = 184KB for one
photograph; now 125KB, and the cards are SHARPER. interior-milano.jpg 147KB now serves the Milano
band and all five Milano cards.
-> Fewer bytes, fewer requests, one decode, no blank-then-pop on the card rows, and the row is
sharp at every breakpoint. The rule generalises: when a composition reuses one image at several
sizes, align the hints rather than optimising each in isolation.
-> NOTE the coupling: the 1.61 crop factor still applies to $others_sizes ('Le altre citta' has no
band above it to share with), and it is written into that sprintf. If Card's aspect ratios or the
source photography's ratio change, that number changes.

**FIX 29 - The footer garland was 192KB fetched eagerly on first paint (inc/footer-render.php).**
Problem: the garland was a hand-written /wp-content/uploads/2026/07/ URL inside a bare <img src>,
so it had no srcset, no intrinsic width/height and no lazy loading - the 2048x404 original was
downloaded in full for an 880px slot, eagerly, for decoration at the very bottom of every page.
inc/refinements.php's own tmk_asset_id() docblock had already predicted exactly this.
-> Resolved by slug through tmk_asset_id('garland-horizontal') and rendered by
wp_get_attachment_image() with loading=lazy, decoding=async and sizes='(min-width: 880px) 880px,
100vw'; the literal URL is kept purely as a fallback so the footer degrades to today's behaviour
rather than losing its artwork.
-> Off the critical path, and it can no longer shift the footer while it loads. It also stops
depending on the upload month, which breaks on any re-upload or migration.
-> **It did NOT get a srcset, and that is a finding, not an oversight: see 18.5.**

**FIX 30 - The ambient decor was 47% of the page's image weight (inc/refinements.php).**
Problem: both PageDecor pieces shared one hint, '(min-width:1024px) 420px, 22vw', but they have
different clamp() widths in shell.css. The browser chose the 768w candidate for both: 171KB for
leaves-banana rendered at 245px and 146KB for snake at 337px - 317KB of 676KB total, for
aria-hidden art at 0.5 opacity behind the content.
-> $pieces now carries a per-piece sizes value, each one its clamp() transcribed: leaves
'(min-width: 1875px) 300px, (min-width: 1000px) 16vw, 160px' (clamp(160px,16vw,300px)), snake
'(min-width: 1909px) 420px, (min-width: 909px) 22vw, 200px' (clamp(200px,22vw,420px)).
-> A shared hint for two differently-sized elements can only be right for one of them.
-> leaves-banana now resolves to its 264w candidate (~21KB instead of 174KB) for a fresh visitor;
snake keeps 768w above 909px only because this attachment has no candidate between 300w and 768w.
-> VERIFICATION NOTE for whoever re-measures: on a warm cache Chrome will keep serving the larger
candidate it already has (observed transferSize 300 bytes, i.e. a 304, on leaves-banana-768x872
after the fix). Confirm this one with an empty cache or by reading the candidate list, not by
reloading.

**FIX 31 - THE MOST IMPORTANT ONE: the reveal mechanism could leave real content invisible, and
a single JS failure blanked the whole page (css/animations/reveal.css, js/animations/reveal.js,
inc/refinements.php).**
Problem, found live: **Roma's four restaurant cards were sitting on screen at opacity 0.** Two
independent causes.
(a) The observer used threshold:0.15. IntersectionObserver reports the state it observes per frame,
so a discrete jump - a wheel burst, Page Down, a restored scroll position, an in-page anchor - can
take an element from below the viewport to ~10% visible at the top edge without it ever having been
15% visible, and the callback then never fires. Measured exactly that: a 214px-tall grid with 22px
showing, is-visible absent, all four children at opacity 0.
(b) Far worse in principle: opacity:0 was the DEFAULT state of the Homepage's city bands and both
of its card grids. If js/animations/reveal.js fails to run for ANY reason - a 404 after a bad
deploy, a JS error earlier in the footer, an extension or content blocker - the entire content area
of the page renders blank while the server happily returns HTTP 200. reveal.css's own comment
already stated the requirement ('reveal utilities must never leave content invisible if a
browser/JS timing edge case is hit') but only guarded the reduced-motion case.
-> (a) threshold:0 with rootMargin '0px 0px -80px 0px'. Any intersection at all reveals, so the
trigger cannot be jumped over; the deeper bottom inset preserves the original intent (reveal once
the element has genuinely entered the viewport, not the instant its first pixel appears) in absolute
px rather than as a fraction of an element whose height varies with the breakpoint.
-> (b) Both hidden states are now scoped to **.tmk-js**, a class set on <html> by a one-statement
inline script printed by tmk_ds_mark_js_active() at wp_head priority 0. Inline and not enqueued,
deliberately: an external script cannot be guaranteed to run before first paint, and the whole
point is that the class exists the first time the reveal rules are evaluated - otherwise the page
flashes its content and then hides it.
-> Progressive enhancement, correctly applied: without JS the page is fully readable with no
animation, which is the right failure mode for decoration. Motion is now genuinely additive.
-> SPECIFICITY WARNING, recorded in the file: .tmk-js .tmk-reveal is (0,2,0), which now TIES with
.tmk-reveal.is-visible (wins on source order, declared after) and with the reduced-motion override
(which was (0,1,0) and had to be raised to (0,2,0) too). Do not reorder reveal.css without
re-checking both ties.
-> Verified after: at rest the below-fold grids are hidden; scrolling reveals with the 60ms stagger;
scrolling back up recovers anything a jump skipped; and the invariant that actually matters - **no
hidden element is ever on screen** - holds at every scroll position tested (measured 0 every time).

**FIX 32 - Footer links failed WCAG 2.2 SC 2.5.8 (css/layout/footer.css).**
Problem: measured 14px tall (column links), 22px (social), 17px (legal). AA asks for 24x24 CSS px
on any pointer target, and the 'inline in a sentence' exception does not apply - these are
standalone navigation lists, not prose.
-> display:inline-block with padding-block:5px on .tmk-footer__col a, .tmk-footer__social a and
  .tmk-footer__legal a.
-> Padding rather than line-height, so the type keeps its designed leading and only the hit area
grows. The columns get 10px taller per row, which the footer's generous vertical space absorbs.

**FIX 33 - The city bands were invisible to heading navigation (inc/card-render.php).**
Problem: Card renders its title as a <span> (faithful to Card.jsx), so a city band contributes
nothing to the document outline. The Homepage's heading outline was: sr-only H1, 'Due culture' H2,
'Le altre citta' H2, 'Il tuo tavolo' H2, 'Resta nel nostro mondo' H3 - i.e. the city bands, which

-> A visually hidden <h2 class="tmk-sr-only"> per city block, carrying the city name.

utility as the page's canonical sr-only H1 (FIX 21). Restores the outline at the same level as
'Le altre citta', which is what the composition actually means.

### 18.7 Tooling reality of this session (read before assuming what is possible)

Browser + WordPress admin + Elementor editor. **No MCP tools of any kind, no DesignSync, no
filesystem, no shell.** What that means concretely:
- **Claude Design IS readable from the browser** and Rule 8 can be satisfied. See Section 16 for
  the endpoints; corrections: the response key is `entries` (not `files`), it is directory-scoped
  so it needs recursion, and Section 17.2's warning stands - GetFile returns base64 in `content`
  even when isBase64 is falsy, so decode unconditionally.
- **Writing plugin files works reliably** by POSTing to /wp-admin/plugin-editor.php with the
  nonce, _wp_http_referer, newcontent, action=update, file and plugin fields taken from the editor
  form. Success = the response contains 'File edited successfully'; a PHP syntax error comes back
  as 'rolled back' and WordPress reverts the file, which is a real safety net. **Do the edits as
  targeted string/regex replacements on the textarea value and assert every replacement matched
  before saving** - never retype a file from an innerText dump, which silently loses formatting.
- **CodeMirror virtualises lines**, so get_page_text on the editor returns only the visible ones.
  To read a whole file: dump the textarea value into a <pre> and read that, or fetch CSS/JS/txt
  directly over HTTP from wp-content (PHP files must go through the editor).
- **Window resizing does not work here** (innerWidth stayed pinned regardless). Use a same-origin
  iframe at the target width as a responsive harness - media queries resolve against the iframe
  viewport, so the measurements are real.
- **Elementor's element cache (24h TTL) still bites.** Any change to markup rendered inside an
  Elementor widget - which includes every [tmk_*] shortcode - needs Elementor > Tools > Clear Files
  & Data before it appears. Confirmed again this session: card markup changes were invisible until
  the cache was cleared. 17.4's rule holds; do not disable the setting.

    header.css     .tmk-navlink.is-active                    (colour AND border-bottom-color)

    shell.css      .tmk-header__nav .tmk-navlink.is-active

### 19.5 Menu Hub - the content import

SOURCE. https://temakinho.it/menu/ - the live production menu, read from the rendered DOM. The

WHAT WAS THERE - 209 rows per language, identical row counts and identical prices in both
(verified programmatically: 0 price mismatches across 209 rows; 124 of 167 dish names are
byte-identical between languages because they are Portuguese/Italian proper nouns). Decomposed:

  167  dishes                 -> menu_item posts
   12  sub-group headers      -> child terms of menu_category  (* ESPECIAL *, * ATUM *, ...)
   13  dotted separator rows  -> DROPPED (see below)
   20  Info & allergeni rows  -> the compliance block (1 coperto, 2 notices, 1 heading, 14

  209

Sub-groups exist in exactly three categories and every dish in them belongs to one:
  ROLLS  (23 dishes) -> ESPECIAL, ATUM, CAMARAO, SALMAO, VEGGIE
  TEMAKI (18 dishes) -> ESPECIAL, ATUM, CAMARAO, SALMAO, VEGGIE
  DRINK  ( 9 dishes) -> MUST DRINK TEMAKINHO, MOCKTAIL

WHAT WAS TRANSFORMED, AND WHY EACH ONE IS NOT A LOSS OF FIDELITY

  T1  13 rows whose entire content is '.............' are dropped. They are the source menu
      plugin's way of drawing a horizontal rule between sub-groups. They carry no words and no
      price. The information they encode - 'a new sub-group starts here' - is preserved with
      more precision, as an actual taxonomy boundary with an actual heading.

  T2  Allergen numbers are lifted out of the description string into an `allergens` meta field.
      All 104 occurrences were verified to be trailing and purely numeric before doing this
      (0 exceptions, 0 non-numeric parentheticals anywhere in 167 descriptions). They are still
      rendered visibly, verbatim, in the published form '(1, 3, 6, 10)'. Lifting them out is
      what makes it possible to ALSO expand them - 'Allergeni: cereali contenenti glutine,
      uova, soia, senape.' - for assistive technology, which the source page cannot do because
      the numbers are buried in a sentence. Same information, twice encoded, nothing removed.

  T3  The highlight star. 4 dishes carry a U+2B50 emoji inside the dish NAME (FRENCH FRIES CON
      PECORINO & TARTUFO, WAKI CHIPS, MIXTO 20 PZ, MIXTO 32 PZ). A screen reader reads that as
      'white medium star' in the middle of a dish name. It is now a labels='star' meta value
      rendered as a real chip. OPEN QUESTION for the client, logged as O7: the source does not
      say what the star MEANS. The chip reads 'In evidenza' / 'Featured', which describes the
      marker's function without asserting 'new' or 'chef's choice'. Confirm and relabel.

  T4  ALCOHOL FREE. 4 mocktails (IPANEMA, COPACABANA, VIRGIN MULE, VIRGIN MOJITO) carry the
      words 'ALCOHOL FREE' written in Mathematical-Italic codepoints (U+1D434 block) inside the
      dish name. Screen readers either spell those out as 'mathematical italic capital A' or
      skip them entirely, and they are unsearchable and uncopyable. So the most safety-relevant
      label on the whole menu was invisible to exactly the users who most need it. Normalised to
      real letters and rendered as a labels='alcohol-free' chip. The WORDS are unchanged.

  T5  Prices. The source publishes bare numbers ('5.5', '9', '2.5'). The number is stored
      untouched in the price meta; display typesets it as '\u20ac\u00a05,50' in Italian and
      '\u20ac\u00a05.50' in English (non-breaking space, tabular figures, locale decimal mark).
      Same price, correctly set. A non-numeric price is echoed exactly as stored, so an editor
      can still write 's.q.' or '10/15'.

  T6  Category and dish names keep the published ALL CAPS (it is the source's typography and it
      suits the brand's caps-heavy voice). The 14 allergen NAMES are stored in sentence case and
      uppercased by CSS, because those same strings are read out inside every dish row and
      fourteen shouted words is not an improvement.

NOTHING ELSE CHANGED. Every category, sub-group, dish name, description, price, allergen code,
the coperto and its price, both legal notices and all 14 allergens are present in both languages.

### 19.6 Menu Hub - the architecture
--------------------------------------------------------------------------------

CONTENT MODEL (inc/content-model.php). Extended, not replaced. menu_item and the hierarchical
menu_category taxonomy were already registered in 5 for exactly this purpose; they were empty.

  menu_item supports  += 'custom-fields'   REQUIRED: the REST API only exposes a post type's
                                           `meta` object when the type declares that support, so
                                           the price / short_description fields registered back
                                           in 5 were never actually readable or writable over
                                           REST. Latent since the model was written.
  menu_item meta      += title_en, short_description_en   the second published language
                      += allergens        comma list of EU numbers, e.g. '1,3,6,10'
                      += labels           comma list of published markers: star | alcohol-free
                      += sort_order (int) the published sequence, which is editorial and cannot
                                          be recovered from the title
  menu_category meta  += name_en, sort_order

WHY NO MULTILINGUAL PLUGIN. WPML/Polylang would duplicate 167 posts and 31 terms into a second
tree whose two halves differ by two strings, and hand the client two content trees to keep in
sync forever. The source itself publishes ONE menu with two label sets. So the second language
rides on the same post. One dish, one price, one allergen set, one editorial position - the
shape of the source. If the site later needs full multilingual content (stories, jobs, events),
revisit; for a menu it would be pure overhead.

SEEDING. 31 terms + 167 posts created over the REST API from the browser, with a wp_rest nonce
lifted from post-new.php's apiFetch middleware. 0 errors, verified 167/167 in the DB. Terms were
created parents-first so children could be attached; each dish carries BOTH its parent term and
its sub-group term so either can be queried directly.

NEW FILES - three, one per existing layer, no new layer invented:

  inc/menu-render.php     ~28KB  data + render + shortcodes + rewrite + hreflang + JSON-LD
  css/pages/menu.css      ~11KB  page layer (the second entry ever in tmk_ds_page_handles)
  js/pages/menu-hub.js    ~5KB   page behaviour

  js/pages/ is a new bucket. enqueue.php's JS map is animations | interactions | navigation |
  components, and this file is none of those - it is one page's own behaviour, which is exactly
  what css/pages/ already means for CSS. Calling it a 'component' would have been a lie about
  its scope; the bucket mirrors a directory that already exists.

  HOW THEY WERE CREATED. WordPress's plugin editor cannot create files. A temporary bootstrap
  was appended to tmk-design-system.php that wrote the three files from embedded nowdoc content
  once behind an option guard, then was removed and the file restored from its pre-bootstrap
  copy (verified byte-length). No endpoint, no external input, nothing left behind except the
  tmk_ds_boot_s6 option. Recorded because a future session will hit the same wall.

SHORTCODES. Three, following the one-shortcode-per-component convention:
  [tmk_menu_hero]        wraps tmk_render_hero() with this page's copy in the read language
  [tmk_menu_hub]         the menu itself
  [tmk_menu_conversion]  wraps tmk_render_cta_banner() likewise
The two bookends are wrapped rather than composed in Elementor because the page exists at two
URLs in two languages, and copy typed into a builder cannot know which one it is being read in.
Wrapping keeps Hero and CTABanner generic - neither learned a second language - and keeps every
string of this page in one file next to the rest of its content.

PAGE COMPOSITION. Page id 216, slug 'menu', title 'Menù'. Built with Elementor, three containers,
one section each - Rule 15 - matching the Homepage's own settings exactly:
  tmkmenu1hero  content_width:full  + padding 0   (so the full-bleed Hero reaches the edges)
  tmkmenu2list  content_width:full  + padding 0   (the hub owns its own max-width and padding)
  tmkmenu3cta   boxed (default)                   (1140px, same as tmkhome5cta)
Template: 'elementor_header_footer' (Elementor Full Width). This is the first page on the site to
use it, and it was necessary: on the theme's default template the content sits inside
Hello Elementor's .page-content, which both caps the width (so the Hero could not bleed) and
applies `.page-content a{text-decoration:underline}` at a specificity the page layer cannot beat
cleanly. It also has one consequence with teeth - see FIX 36.

  The containers were created programmatically with Elementor's own command API from the editor
  ($e.run('document/elements/create') then 'document/save/default'), which is far more reliable
  than dragging widgets and produces identical data. Use this for future pages.

BILINGUAL URLS. /menu/ (it) and /menu/en/ (en). One rewrite rule maps the /en/ segment to the
same page with tmk_lang=en; get_canonical_url is filtered so the English page is canonical to
itself; wp_head emits a reciprocal hreflang pair plus x-default. The source page has one URL and
a JS tab switcher, which means only its Italian menu is indexable and neither language can be
linked or shared - this is strictly better and cost ~30 lines.

  TRAP: the rewrite rule is registered on init at priority 5, NOT 21. The rewrite-flush guard in
  tmk-design-system.php runs on init at 20, so a rule added at 21 is never in the rules array
  when the flush happens and /menu/en/ 404s until something else flushes. Cost one debug cycle.

QUERY SHAPE. One WP_Query for all 167 dishes, ordered by sort_order, then grouped in PHP using
get_the_terms() against WP_Query's own primed term cache. The obvious shape - one query per
category - is 19 queries plus 19 term lookups on a page that never changes between requests.
Because sort_order is unique and ascending WITHIN a category, iterating the whole set in that
order and bucketing preserves each category's published order and keeps sub-group runs
contiguous, so group order falls out for free.

STRUCTURED DATA. schema.org Menu -> MenuSection -> (MenuSection) -> MenuItem with Offer/price/
priceCurrency, emitted in the read language only, from the tree that is already in memory. 31KB
of the page's 247KB, highly repetitive so it compresses to a fraction. O8: it should be pointed
at from a Restaurant node's hasMenu when the Location template exists - that is where the
Restaurant entity legitimately lives; inventing one on this page would mean inventing an address.

CACHE CHECK. elementor_element_cache_ttl is 24h on this install, which would have been a real
defect: a price edited in the CPT could take a day to appear. Tested empirically - edited a
price over REST, loaded the page (twice, so any cache would be primed), edited again, loaded
again. Both edits appeared immediately and the original price was restored. Shortcode widget
output is not being served stale. Re-test if that TTL or Elementor's optimised-markup
experiments change.

  D-M6  The hub is --container-wide (1280), not --container-standard (1040). With a 280px rail

        is what makes two readable dish columns possible at all.

  D-M7  The identity rail is position:sticky from 1024px up (top = measured chrome + space-4).

        reading. It is the editorial spread's payoff, and it is free.

### 19.8 FIX 36-40 - site-wide defects this milestone surfaced
--------------------------------------------------------------------------------

FIX 36  THE MISSING main LANDMARK (inc/accessibility-landmarks.php).
        14's note explains why the content wrapper is a <div id="main"> and not <main>: Hello
        Elementor's page template already emits <main id="content">, so a <main> here produced
        two landmarks. That reasoning holds only while the THEME emits one. Elementor's own page
        templates - 'elementor_header_footer' and 'elementor_canvas' - do not. The Menu Hub is
        the first page to use one, and it shipped with ZERO main landmarks: a skip link landing
        on a plain div, with no way for a screen-reader user to know they had reached the content.
        The wrapper tag now follows the template - <div> where the theme owns <main>, a real
        <main> where nothing else provides one. Verified: Menu 1 main (id=main), Homepage still
        1 main (the theme's id=content) with the wrapper still a div.
        ANY future page on an Elementor template inherits the fix automatically.

FIX 37  HEADING ORDER, SITE-WIDE (inc/header-render.php + css/layout/header.css).
        The mega menu rendered each city as a bare <h3>. The mega menu lives in the site header,
        i.e. BEFORE the page H1 in document order, so EVERY page on this site opened its outline
        at level 3 and pushed the real H1 into an out-of-order position. Seven of them. A mega
        menu is navigation: its structure is carried by the region label, the lists and the links,
        and screen-reader users move through it by list, not by heading. Now
        <p class="tmk-megamenu__city">, with the class added to the existing rule so the visual
        treatment is byte-identical (verified: Londrina Solid 20px, unchanged).
        Verified: Menu and Homepage both now start at H1 with 0 skipped levels.

FIX 38  DUPLICATE ID FROM THE LOGO (inc/logo.php). The inlined SVG carries Illustrator's
        id="Livello_1" on its root, and the logo is inlined twice on every page (header and
        footer), so every document on the site had a duplicate id. Nothing references it - the
        artwork has no url(#...) references and takes its colour from currentColor - so the root
        id is now stripped in the same sanitiser that adds the class.

FIX 39  DUPLICATE ID FROM THE NEWSLETTER (inc/newsletter-render.php). wp_nonce_field() gives the
        hidden input an id equal to its name, and NewsletterCapture renders twice on the Homepage
        (its own section per D-H3, plus the footer). Replaced with a hand-rolled hidden input
        using the instance-unique $uid the email field already had. The referer field is dropped;
        the AJAX handler validates with check_ajax_referer() on the nonce field alone, and the
        client JS posts new FormData(form) so the field is still sent by name.
        Verified: Homepage duplicate ids 0 (was 2 distinct duplicates before FIX 38+39).

FIX 40  THE NAV NOW HAS A DESTINATION (inc/header-render.php, inc/footer-render.php). Every
        primary nav label resolved to '#' . slug, because no destination page existed. The Menu
        Hub is the first real one. tmk_nav_destination() asks the site instead of hardcoding: a
        published page answering to the label's slug gets its real permalink and aria-current
        when it is the page being read; the hub additionally gets the permalink of the LANGUAGE
        being read, so a visitor on /menu/en/ is not silently sent back to Italian. Labels with
        no page keep their placeholder anchor - this adds a destination, it does not invent
        navigation. Applied to the desktop nav, the mobile drawer and the footer's Esplora list.
        Verified: header, drawer and footer all resolve to /menu/, and MENU carries
        aria-current=page on the hub (in the newly AA-compliant on-light accent).

TWO TRAPS RECORDED, both cost a debug cycle and both will recur:

  TRAP-1  scroll-padding-top and scroll-margin-top ADD UP. css/refinements/shell.css already
          sets html{scroll-padding-top:var(--space-9)} site-wide so anchor jumps clear the sticky
          header. Compensating for the header AGAIN with scroll-margin-top on the target
          overshot every quick-nav jump by 96px. Anchor offset is the shell's job; a page may add
          air (now var(--space-3)) and nothing more. Verified: all four probed anchors land at
          108px, 19px clear of the 89px header.

  TRAP-2  the [hidden] attribute loses to any class-level display. Every block in a modern DS
          file is display:grid or display:flex, and .tmk-menu-empty{display:grid} silently beat
          the UA sheet's [hidden]{display:none} - the empty state was permanently on screen and
          the text filter hid nothing. Re-asserted at attribute specificity inside menu.css, so
          no !important was needed. The hazard is SYSTEM-WIDE: any component that ships a
          display and expects `hidden` to work has the same bug. Logged as O10 rather than
          smuggling a global [hidden]{display:none!important} into css/base/base.css, which is a
          base-layer decision and should be taken deliberately.

### 19.11 Tooling notes new to this session
--------------------------------------------------------------------------------

  - window.name survives a cross-origin navigation in this browser, which is how 41KB of menu
    JSON was carried from temakinho.it into the localhost origin without a proxy; it was then
    persisted to localStorage on the WordPress origin so it outlived every later reload.
  - The wp_rest nonce can be lifted from /wp-admin/post-new.php's apiFetch middleware; that plus
    the REST API is the fastest safe way to seed hundreds of posts.
  - Elementor documents can be built programmatically from the editor with $e.run(
    'document/elements/create' | 'document/elements/settings' | 'document/save/default').
    Element ids can be supplied in the model, so containers get readable ids like the Homepage's.
  - The plugin editor's save must be verified by READING THE FILE BACK. WordPress silently rolls
    back a save that would fatal, and the response still contains the word 'updated', so a
    naive success check reports a save that never happened. This session's first enqueue.php
    edit was rolled back for a missing '//' and only the read-back caught it.
  - The javascript_tool result is filtered: long ';'-separated key:value text (i.e. any token
    file) trips the cookie/query-string guard. Dump to a <pre> and use get_page_text instead.
  - Programmatic scrolling (window.scrollTo, location.hash, .click() on an anchor) does not move
    the top-level page in this harness. Use the computer tool's scroll for the real page, and an
    iframe for measurements - inside an iframe all of it works normally.
